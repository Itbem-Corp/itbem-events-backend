# Automation Agent Directory v1

`GET /api/automation/agents` is a protected operational snapshot. Platform administrators (Root 1 or Root 2) may use the platform workspace globally or select `client_id` / `project_id`. Organization-workspace users may query only an explicit client or project; project access uses the canonical Delivery project-view policy, and a client-level response is further intersected with projects for which that user's membership role grants view access. A client filter covers that client and its active descendants; in organization workspace the selected client must also be inside the current organization tree. A project filter is resolved against a non-deleted project before any data query. When both are present, the project must belong to the selected client subtree or the API returns a generic `404`. IDs are filters, never authorization credentials.

The v1 response is `{ schema_version, generated_at, summary, agents, queue_lanes }`:

- `summary` reports configured profiles, live instances, active task runs, currently available non-draining slots, queued task count and 30-day spend in integer micro-USD. In a client/project/organization-filtered response, activity, queue and spend aggregates are restricted to that hierarchy. Because heartbeats have no client/project ownership, only workers with an active run in the selected scope appear; `availability_known` is false and the API does not present global free slots as scoped availability. Profiles remain shared platform configuration, while their scoped status and history reflect only matching activity.
- `agents` contains the logical profiles from `AutomationAgentProfile`; each profile reports whether it is configured active, a `capabilities` list of declared descriptive capabilities, and a separate `operations` list restricted to the backend's supported routing operations. Neither field is an effective permission grant. Each profile nests recent process heartbeats and only the running/cancellation-handoff tasks that actually have that instance's `worker_id`. Each active run may link to its client, project and delivery work item. `started_at` is returned only when an append-only `claimed` or `lease_reclaimed` event matches that task's current `run_id` and `worker_id`; legacy or missing events stay unset, and task `created_at` is never used as a fallback.
- `queue_lanes` groups queued tasks by operation and includes the oldest queued timestamp. These are shared queue counts, not assignments to individual agents.

The roster includes heartbeats seen in the preceding 30 days. Instance liveness becomes offline after 90 seconds without a heartbeat. Cost and unique run totals use the preceding 30 days; lifetime execution evidence remains in the append-only automation ledgers. This is a current operational view, not paginated task history. The response deliberately omits task inputs/prompts, output/error payloads, private object references, usage JSON, workspace readiness, hostnames, local paths and credentials. `operations` is filtered against the backend routing allow-list; `capabilities` contains only declared capability labels and is not an ACL.

`GET /api/automation/agents/stream` is the authenticated SSE invalidation channel consumed by the dashboard's `useAgentDirectoryStream` hook. This screen is intentionally a platform-wide operations view, not a tenant/project report: only platform administrators (Root 1/2) can connect, and the query string has no tenant/project scope that could be mistaken for row-level authorization. A non-platform product surface also strips platform-root authority before the controller check. Tenant/project views must use their own scoped APIs rather than this directory stream.

The stream emits `snapshot` on connection and `update` only after its safe aggregate fingerprint changes. Each event contains exactly `{ revision, generated_at }`; `revision` is a fresh random 256-bit hex invalidation token and the deterministic aggregate fingerprint is never serialized. It contains no project IDs, agent details, prompts, credentials, or payloads. The browser hook refetches the snapshot/history through their regular authenticated APIs on these events. The server checks Root 1/2 at connect and every 12 seconds during the stream, closing immediately on authorization loss. Streams roll over cleanly after 55 seconds; the hook reconnects with current request authentication, while the server sends 12-second SSE comment heartbeats (within the hook's 35-second read watchdog). Polling is every second while assignments/steps are active and every three seconds while idle. The response is `private, no-store`; a fresh snapshot on every reconnect makes replay cursors unnecessary.

`GET /api/automation/agents/:agentKey/history` is the cursor-paginated timeline. It combines database-captured append-only task lifecycle events (creation, claim, lease reclaim, reassignment, attempt and status changes), legacy task snapshots only when no lifecycle event exists, immutable inference/tool ledger rows, append-only plan-step events, and sanitized step-activity events. Lifecycle rows preserve current and previous run/worker/agent/machine/instance identifiers; identifiers are allow-listed before projection. The query can filter by time, client, project, work item, worker, machine, agent instance, run, operation, status, and provider. These identity filters are correlation metadata, not authorization boundaries. `platform` workspace requires a platform administrator; requested client/project records are resolved server-side, and a project must belong to the selected client subtree when both filters are present. `organization` workspace always intersects the selected organization; requested clients must be within that organization tree and projects must pass the canonical project-view authorization. A non-root caller using an organization-level query is further restricted to the projects for which their membership role grants view access. A page returns at most 100 rows, and `to` is exclusive. It projects safe context, token/cost totals, provider/model labels, allow-listed actions and fixed summaries—never prompts, raw output/errors, object references, command text, file paths, or hidden reasoning. The opaque cursor binds pagination to the agent, workspace, actor, selected hierarchy and effective authorized project set.

## Machine identity and callback security

`GET|POST /api/automation/agent-instances` and `DELETE /api/automation/agent-instances/:id` remain primary-root-only operator controls. Registration binds an active `agent_key`, canonical lowercase UUID `machine_id`, and an unpadded base64url Ed25519 public key. The response and roster expose only the instance ID, public-key SHA-256 fingerprint, status, and timestamps; the public key itself is not re-rendered and the private key is never accepted by the API. Re-enrollment with a different key requires revoking the old identity first. Revocation takes effect on the next request.

Gateway workers can enroll automatically through `POST /api/internal/automation/agent-instances/enroll`. The request must carry the exact role/lane gateway token and a domain-separated Ed25519 proof over the active `agent_key`, canonical `machine_id`, and public key. The endpoint issues the instance ID; it does not accept an ID from the worker. Repeating the same enrollment is idempotent. A conflicting key or revoked machine is rejected; primary-root operator re-enrollment remains required after revocation. The gateway token is already required to receive lane work, remains lane-bound, and is never the callback root secret.

The local agent creates its stable machine UUID and private Ed25519 key on first use and protects them in OS-protected local state (DPAPI on Windows; user-only file permissions on Unix-like platforms). At first service start, `--ensure-registered` performs the signed gateway enrollment and stores the server-issued ID in the same private state directory, scoped by `agent_key`. Keep that state directory across restarts. Systemd runs this step before the non-mutating doctor and auth probes; direct gateway-mode starts do the same. If secure storage fails, enrollment fails closed. Legacy AWS-direct workers still use the primary-root enrollment path. Each callback signs the HTTP method, exact request URI (including query), raw-body SHA-256, instance ID, Unix timestamp, and fresh UUID nonce. The API verifies the signature and a ±90-second clock window; a database uniqueness constraint rejects nonce reuse across replicas. TLS remains required outside explicit loopback development. Provider API keys and the control-plane signing keys remain in the cloud and are never forwarded to the worker.

The server derives the callback's profile and machine identity from the enrolled public key, rejects mismatches in the body, and independently validates task assignment, project scope, lease, and fencing state. A stable machine ID is used only for affinity and attribution; it is not a tenant boundary or host fingerprint. Workspace readiness in a heartbeat is still an operational self-report, not cryptographic attestation. `AUTOMATION_CALLBACK_SECRET` is not an agent credential and must not be delivered to any local agent or sandbox.

## Timeline cost coverage

Both `GET /api/automation/agents/:agentKey/history` and
`GET /api/automation/traces` include `cost_coverage` for only the events in the
returned cursor page (`scope: returned_page`). `verified_usd_executions` counts
inference/tool rows with USD currency and a concrete pricing basis;
`unpriced_executions` counts inference/tool rows whose currency or pricing
basis is missing, non-USD, legacy, or unpriced. Such a row retains observed
tokens but omits the amount and reports `cost_pricing_status: unknown`. A
numeric zero is a verified USD amount only when its status is explicitly
`verified_usd`; page counters must not be used as totals for the entire query.
